# 3.2.0 功能说明：转诊材料、院内审核与接收衔接

本版按 9 月 21 日修改建议完善三模块的资料录入和业务衔接。下表描述当前代码提供的操作与结果；部署状态和实际按钮验收须以 [验证记录](verification.md) 中相应版本的记录为准，不沿用旧版验收结论。

| 修改项 | 操作入口与形成的结果 | 当前边界 |
| --- | --- | --- |
| 病历与影像附件 | 上转工作台添加图片、PDF 或 DICOM；随申请供审核方和接收方查看、下载 | 每份 5 MB、每单 10 份；不提供 DICOM 阅片或自动影像诊断 |
| 院内诊疗信息导入 | “院内数据接入”载入示例就诊信息，或导入 JSON；核对后带入上转草稿或下转患者表单 | 东华、嘉和为示例入口，真实 HIS/EMR 接口尚未接通 |
| 医务审核 | 新上转申请先进入来源医院审核视图；填写审核人、意见、医保及材料核对信息 | 属于平台内人工记录，没有真实医院身份认证或院方审批接口 |
| 退回与重提 | 审核退回后补充病例、附件和医保信息，重新提交；原记录与操作事件保留 | 重新审核后才能进入上级接收队列 |
| 消息提醒 | 审核与接诊待办、退回补充提示可查看、标为已读并进入对应申请 | 站内消息可用；短信、微信显示未配置，不声称已发送或送达 |
| 下转患者建档 | 新建患者、编辑患者信息、填写诊疗摘要与后续服务需求 | 编辑不清空历史，新患者没有测量数据时显示空态 |
| 独立下转接收中心 | 按待接收、已安排或全部申请查看，复核交接并登记科室、床位/地点及服务安排 | 平台登记不代表下级医院已经锁定真实床位 |
| 可选工作时间 | 医生详情显示含今天的近 7 日上午/下午时间，上转择期可直接选时段 | 排班和余量为预设参考；过时时段不可选 |
| 候选排序 | 专业匹配优先、最近接诊时间优先、意向登记较少优先，可筛选近期可登记 | 排序不改变专业匹配分；平台意向不占医院真实号源 |

## 上转操作顺序

1. 手工录入或导入患者资料，补充病例、附件及医保材料信息。
2. 匹配有照片的医生，查看依据与工作时间，选择择期意向时段。
3. 复核后提交医务审核。审核通过转入上级接收中心；退回则补充后重新提交。
4. 接收人员登记科室和就诊或床位意向，记录变为“已登记待核实”。
5. 在上转记录与消息提醒中跟进状态及操作历史。

急症提示保留立即联系接诊团队的安排。紧急联系与平台审核同步进行，不等待普通排班或页面审批；系统不代替转运协调、救治或院方确认。

## 下转操作顺序

1. 新建或选择患者，核对上级诊疗摘要、当前阶段、后续服务与交接要求。
2. 选择下级接收团队及计划日期，提交下转。
3. 在“下转接收中心”复核交接并登记接收地点和后续安排。
4. 从接收队列进入同一患者的连续照护，按日期录入和查看监测。
5. 发生突发情况时保留原始记录，由 AI 整理后供上级复核；人工登记处理结果。

## 数据保留和升级

服务器已经存在的业务记录、接收状态、患者、计划和监测历史保留。新提交的上转申请必须经过本版审核流程。首次迁入的旧浏览器上转记录若没有审核字段，将保留原接收字段和历史事件，同时转为待审核并加入迁入说明；旧浏览器不能覆盖已经保存的新版审核结果。

转诊附件存入 `DATA_DIR/attachments`，与业务快照一样放在独立持久目录，更新应用代码不会覆盖。文件上传与申请关联分开：上传成功即保存文件，提交后关联申请；移除草稿关联不等于永久删除服务器文件。备份、搬迁服务器时应复制整个持久目录，并保留私有权限。API Key 仍仅由服务器环境配置读取，不进入业务记录、前端或发布包。

新增的审核状态、动态患者和附件引用需要新版读取逻辑。写入这些数据后，不应直接回退到不支持它们的旧版程序，更不应以旧数据快照覆盖当前记录；应先保留完整数据备份，再使用兼容记录结构的修复版本。

## 尚待真实机构接入的能力

HIS/EMR、医保结算、真实排班与号源、床位、设备监测、短信和微信尚未连接外部服务。医保核对不等于报销判断；审核和接收登记不等于院方已收到；消息已读不等于外部渠道送达；参考余量与平台意向不产生真实挂号或床位占用。

当前访问者仍共用同一个服务器工作区，角色视图不等于账号权限隔离。导诊图片识别和问答继续使用配置的模型服务；普通附件上传不会自动调用模型。详细操作见 [三模块说明](care-platform.md)，部署和备份方式见 [Linux 部署说明](linux-deployment.md)。
